# A generator's runners dial the management address detected for it; the env vars are fallbacks

Every URL a k6 runner dials back to the management node (the summary upload and the GO signal on the filer NodePort, the payload images on the S3 NodePort) used to be built on one global address: `DFAAS_SYNC_PUBLIC_URL` or `HOST_IP` in the operator, `SEAWEEDFS_PUBLIC_URL` or a node IP in the gateway. A deployment spread over several sites has no such address: each site reaches the management node on a different interface, and a single value always leaves some generator dialling an address it cannot route to.

The generator itself already knows the right address, because the SSH session that provisions it arrives from the management node. So the k6 playbook reads the first field of `$SSH_CONNECTION` on the generator, probes the filer NodePort with it from there, and records it only when it is IPv4 and the probe gets an answer. The operator copies it into `status.k6Nodes[].managementAddress` and builds that generator's `DFAAS_SUMMARY_URL`, `DFAAS_SYNC_URL` and `DFAAS_ASSET_BASE` on it. A detected address wins over every env var. The env vars stay as fallbacks for a generator with no address: an older playbook, an Environment not re-provisioned since, or a detection that failed or could not be verified.

Detection never fails provisioning. It replaces settings that worked on a single-site setup, so a generator it cannot place keeps the old behaviour instead of turning the Environment `Failed`. A refused connection counts as verified: on a fresh management cluster SeaweedFS is installed in `ProvisioningMonitoring`, after the k6 Job, so nothing listens on the port yet, and requiring an HTTP answer would record nothing for the first Environment provisioned there. IPv4 only, because the k3s the playbook installs is single-stack: the probe runs on the host network and would pass for an IPv6 address that no runner pod can dial. Widening it means a dual-stack k3s install too; the operator side already accepts IPv6.

## Consequences

- An explicit `DFAAS_SYNC_PUBLIC_URL` or `SEAWEEDFS_PUBLIC_URL` no longer overrides a detected address, and nothing else does. A wrong address is reported by the dispatch probe (`K6Dispatched` reason `DispatchedUnreachable`, whose message names the URL tried and says it was built on the detected address) and is fixed by opening the port or re-provisioning, not by setting a variable.
- Accepting a refusal means the provisioning probe proves less than a successful fetch. An SSH path through a bastion or NAT, or a CNI that does not masquerade the Ansible Job's traffic, can record the address of some other host that happens to answer. The dispatch probe catches it only on the filer port, and only once a test runs. Nothing probes the S3 NodePort that `DFAAS_ASSET_BASE` points at: it is assumed open wherever the filer NodePort is, and a generator that cannot reach it finds out from the script's `setup()` abort.
- The address reaches an Environment only through a provisioning run: one that was `Ready` before the upgrade needs a spec edit. The field is a CRD status field, so an operator running against the old CRD has it pruned and every generator falls back without notice.
- Asset relocation is keyed on the config name `seaweedfs-default`. A `SEAWEEDFS_PUBLIC_URL` with a path prefix or `https` (a reverse proxy) is bypassed for runners that have `DFAAS_ASSET_BASE`.
