# Architecture

This document describes the operator's internals: the code layout, the two state machines, the monitoring stack and its addresses, dispatch, the synchronized start, the export, and how failures are retried. [overview.md](overview.md) gives the system view first; [glossary.md](glossary.md) defines the terms.

The operator is one Go binary (`cmd/main.go`) that runs two controllers, `EnvironmentReconciler` and `LoadTestReconciler`, in one controller-runtime manager. Each controller runs one reconcile at a time (the default of one worker). It creates no VMs: every machine already exists, and the operator reaches it over SSH (through Ansible Jobs) or, for generators, through the Kubernetes API of the generator's own k3s.

## Environment

### Phases

```text
"" -> ProvisioningVMs -> ProvisioningInfra -> ProvisioningMonitoring -> Ready <-> Unreachable
                          |- Ansible Job, DFaaS nodes  -|
                          |- Ansible Job, generators  -|   in parallel, then fan-in
                                                                       Failed (terminal, until a spec edit)
any phase, on a spec edit (generation drift) -> ProvisioningVMs
```

| Phase | Meaning | Exit |
| --- | --- | --- |
| `""` | First observation. | `ProvisioningVMs` on the next pass. |
| `ProvisioningVMs` | The write that enters it records `status.provisioningGeneration`. The operator dials `<ip>:22` on every node (2 s timeout per node). | `ProvisioningInfra` when all answer. Not all: requeue after 10 s. After 3 consecutive unreachable rounds: `Unreachable`. |
| `ProvisioningInfra` | First waits until any Ansible Job of an older generation is gone. Then runs the two Ansible Jobs in parallel (one per role). A surviving stream is allowed to finish when the other fails, so both Conditions stay coherent. | `ProvisioningMonitoring` when both succeeded. `Failed` when either failed, after both finished. |
| `ProvisioningMonitoring` | Installs the three Helm releases, waits for the pods, writes the Prometheus scrape targets, then writes `status.k6Nodes[]` (including each generator's `managementAddress`) and `status.dfaasNodes`. Runs after the Ansible Jobs so that the DFaaS nodes' metrics endpoints exist before the first scrape. | `Ready`. `Failed` after 5 consecutive Helm failures. |
| `Ready` | Infrastructure and monitoring are up and `status.observedGeneration` equals `metadata.generation`. A periodic SSH probe runs (see below). | `ProvisioningVMs` on a spec edit. `Unreachable` after 3 consecutive failed probe rounds. |
| `Unreachable` | Not terminal. Nodes stopped answering port 22. Re-probed every 30 s with no limit. | `Ready` when the nodes answer again, the infrastructure was already up and the spec did not drift. `ProvisioningInfra` when the infrastructure was not up yet. `ProvisioningVMs` on a spec edit. It never moves to `Failed` by itself. |
| `Failed` | Terminal: an Ansible stream failed, or the Helm budget ran out. No automatic retry. | `ProvisioningVMs` on a spec edit, or delete and recreate. |

`Ready` and `Failed` are the settled phases: entering either copies `status.provisioningGeneration` into `status.observedGeneration`. `Unreachable` is not settled and does not stamp it.

A node that stops answering is not a failure. The probe is a TCP dial to port 22 and nothing else, so `Ready` can come back before k3s, OpenFaaS and the agent have, and a LoadTest that is already `Running` is not affected by the Environment's phase.

### The Ready-state health probe

While an Environment is `Ready` and its generation is settled, each pass re-asserts the Prometheus target file and then runs `reconcileReadyHealth`. The probe runs at most once per 60 s (20 s while `NodesReachable` is `False`), and the decision is confirmed against an uncached read of `status.lastHealthCheck`: the informer cache lags the controller's own status write, and a stale read once let a second probe through milliseconds after the first, which used up the three-round tolerance in seconds. A healthy round stamps `NodesReachable=True`, `VMsReady=True` and `status.lastHealthCheck`. After 3 consecutive failed rounds the phase becomes `Unreachable`. The miss counter (`health-misses`) is separate from the provisioning counter (`ssh-attempts`) so that the two never overwrite each other.

### Generation drift: how a spec edit restarts provisioning

A spec edit increments `metadata.generation`. At the top of every reconcile (after the Ready health route), `handleGenerationDrift` applies one rule to every phase. In a settled phase it compares `status.observedGeneration`; in any other phase it compares `status.provisioningGeneration`, the generation the current run applies. A recorded value of 0 means "no record" and is never drift. On drift the operator:

1. deletes the Ansible Jobs of older generations (matched by the label `dfaas.io/generation`, listed through the uncached reader, deleted with foreground propagation so a Job outlives its pods) and the inventory Secrets of those generations, which hold node credentials;
2. sets `Ready`, `VMsReady`, `DFaaSNodesReady`, `K6Ready`, `InfrastructureReady`, `MonitoringReady` and `NodesReachable` to `Unknown` with the reason `Updating`;
3. moves the phase back to `ProvisioningVMs`.

`ProvisioningInfra` then waits (10 s requeue) while any Job of an older generation still exists, so two generations of playbooks never run on the same machines. Because a settle copies `provisioningGeneration` and not the current `metadata.generation`, an edit that lands in the middle of a run stays drift instead of being recorded as installed without ever reaching Ansible.

`status.provisioningGeneration` is a CRD status field. Helm never upgrades CRDs, so on an upgrade apply the new CRDs first; otherwise the API server prunes the field and a mid-run edit is recorded as installed ([cross-repo-contract.md](cross-repo-contract.md#changing-a-crd-field)). The SPA reads a non-zero `observedGeneration` below `generation` as "update in progress".

### Ansible Jobs

One Job per role, built by `ansible.Manager.CreateJobForRole`:

- name `<env>-infra-<suffix>-<uid8>-g<generation>-job`, where the suffix is `vms` (DFaaS nodes) or `k6` (generators) and `uid8` is the first 8 characters of the Environment UID. Including the UID and the generation means a recreated or edited Environment never reads the status of an earlier run. The name goes through `ansible.BoundedJobName`, which caps it at 63 bytes by cutting the Environment-name prefix (see [known-limitations.md](known-limitations.md#resource-names-63-bytes-for-a-loadtest-51-for-a-testrun));
- image `alpine/ansible:2.18.6`. The entrypoint installs `py3-pip` with `apk`, `pip3 install kubernetes`, and the Galaxy collections pinned exactly in `templates/requirements.yml`, then runs `ansible-playbook` with SSH host-key checking off;
- `BackoffLimit: 3` (four attempts), `ActiveDeadlineSeconds: 1800`, `RestartPolicyNever`, failed pods retained (`PodReplacementPolicy=Failed`);
- mounts: an inventory Secret, a playbook ConfigMap holding the embedded playbook for the role, and a ConfigMap with the HAProxy, OpenFaaS and per-VM Prometheus values;
- a per-Environment ServiceAccount with a Role that allows `get`, `list`, `create`, `update` and `patch` on Secrets in the Environment's namespace, used by the generator playbook to push the kubeconfig Secret back.

The TTL is not set at creation. After the Job settles, the reconciler patches it: 600 s on success, 24 h on failure. On success the TTL is stamped only once both streams have finished, so auto-deletion cannot trigger a recreate in the middle of the fan-in.

Because of `BackoffLimit: 3`, one failed pod is transient. The reconciler decides a Job is terminal from its `Complete` and `Failed` Job conditions, never from the failed-pod count. While a Job has failed pods, the stream's Condition message carries the attempt count and the failing task name, read from the log tail of the newest failed pod (for example `k6 Ansible Job failed after 4 attempt(s) at task: Install k6-operator chart; check logs`, where `k6` is the role label). The playbook task names are therefore static strings: the parser reads them back from the pod log.

The inventory is plain INI text built by `buildInventory`. For DFaaS nodes, node *i* gets a bootstrap list made of every DFaaS node listed before it (`buildInventory` receives only the nodes of the same role), as `/ip4/<ip>/tcp/31600/p2p/<peerID>` multiaddresses, so the first DFaaS node is the seed and dials nobody. The libp2p identity of each DFaaS node is an ed25519 key stored in the Secret `<env>-libp2p-keys` (created on first use, owned by the Environment, reused on every later pass so peer IDs are stable). To pin a peer ID across a delete and recreate, create that Secret with your own PKCS#8 keys before applying the Environment. The port 31600 is `libp2pBootstrapPort` in `ansible/job.go` and must equal the NodePort the dfaas-agent chart exposes ([dfaas-agent.md](dfaas-agent.md)).

### What the playbooks do

`setup-nodes.yml` (DFaaS nodes), in order: record-and-compare the role marker (`/etc/dfaas-role`) and wipe k3s on a role change; disable APT auto-upgrades and UFW; set kernel parameters; install k3s only when missing; pin `node-ip` to the address the operator uses; install Helm only when missing; add the HAProxy, Prometheus and OpenFaaS chart repositories and install the three releases; install `faas-cli` only when missing; point the OpenFaaS gateway at the node's Prometheus; prune functions that are not in the spec and deploy the ones that are; install the dfaas-agent Helm release (chart `0.1.3`, image `ghcr.io/isired01/dfaas-agent:dev`); restart the agent when its release changed; record the role.

`setup-k6-nodes.yml` (generators), in order: detect the management address (see [cross-repo-contract.md](cross-repo-contract.md#per-generator-management-address)); the same role marker logic; install k3s only when missing, with a TLS SAN for the address the operator uses; install Helm only when missing; install the `grafana/k6-operator` chart pinned at `3.7.0`; rewrite the server URL of `k3s.yaml` to `https://<ip>:6443` and push it as the Secret `<env>-<nodeID>-kubeconfig` (server-side apply, labelled `dfaas.io/env` and `dfaas.io/node-id`, carrying the annotation `dfaas.io/management-address`, owned by the Environment); record the role.

The playbooks, the HAProxy, OpenFaaS and Prometheus values, and the monitoring charts are compiled into the operator binary. A change to any of them needs a new operator image (or a restart of `make run`) and a re-provisioning of the Environment.

### Deletion

The Environment finalizer `dfaas.dfaas.io/environment-finalizer` does the following before it releases the object:

1. It deletes the LoadTests that target the Environment and are live, hold an unreclaimed runner, or have dispatched, and waits (3 s requeue) until each is gone. The LoadTests' own finalizers need the kubeconfig Secrets to reach the generators, which is why they go first. The wait is bounded per test: 3 minutes (`deletionReclaimBudget` plus one minute) from that test's own `DeletionTimestamp`. After that the Environment prunes with the test still finalizing.
2. It removes the Environment's file from the shared `prometheus-targets` ConfigMap.
3. It deletes the generator kubeconfig Secrets.

The candidates are picked by `spec.targetEnvironment`, not by owner reference, because under `kubectl delete --cascade=orphan` the garbage collector strips the owner references of the dependents while this loop runs. A finished, dispatched test is kept when the Environment carries the `orphan` finalizer or when the test has no owner reference to this Environment. `--cascade=foreground` lets the garbage collector delete the Secrets in parallel and defeats the ordering; background (the default, and what the gateway sends) keeps it. The finalizer is only released after the target cleanup succeeds, because the shared ConfigMap does not cascade; a failed cleanup is retried.

The operator never removes the monitoring stack or anything on the VMs when an Environment is deleted.

The status writer stamps the aggregate `Ready` Condition in the same write that sets the phase. Messages are sanitised of timestamps, pod UIDs and request IDs, so that `LastTransitionTime` stays stable across reconciles.

The UI renders Condition messages verbatim, so the format of a message is part of the cross-repo contract. The SPA couples to reason strings in two ways: it looks up the abort explanation by `Ready`/`UserAborted`, and its curated reason table must give every reason that means "dead" the tone `error`. `api/v1/inventory_test.go` keeps a `terminalFailure` table with one row per reason constant and fails on a reason that is unclassified or that nothing stamps. See [cross-repo-contract.md](cross-repo-contract.md#condition-reasons).

## LoadTest

### Phases

```text
""  (not admitted) -> Pending      every admitted test, before anything remote happens
""                 -> Failed       startAt without suspended, or a non-draft test on an Environment that is not Ready
Pending -> Running -> Exporting -> Completed
   |          |           |
   +----------+-----------+-----> Failed
Pending / Running ---- spec.stop=true, or kubectl delete ----> Aborted
```

| Phase | Meaning | Exit |
| --- | --- | --- |
| `""` | Not yet admitted. The first pass runs the two create-time checks and writes `Pending`. Nothing remote happens here. | `Pending`, or `Failed` on `startAt` without `suspended`, a non-draft test on a non-`Ready` Environment, or an Environment that does not exist. |
| `Pending` | Waiting for: draft activation, the scheduled time, the Environment to be `Ready`, its turn in the queue, dispatch, or the sync barrier. | `Running` when every TestRun is applied (with `syncStart`, once the GO signal is published). `Failed` when the dispatch budget runs out, the barrier fails, the Environment stops being `Ready` after TestRuns were applied, a `perNodeLoad` node has no usable generator, or (with `syncStart`) a generator resolves no GO URL. |
| `Running` | One remote TestRun per `perNodeLoad` entry has been applied. Every generator is polled once per round, every 5 s. | `Exporting` when every TestRun reports `finished` or `stopped`. `Failed` when any reports `error` once all have ended, when a generator becomes unusable, after 15 consecutive failed rounds, or when the Environment is not found. |
| `Exporting` | After the cool-down, the exporter Job runs. `spec.stop` is no longer honoured. | `Completed` on Job success. `Failed` on Job failure or a missing explicit S3 config. `Aborted` only by deleting the test. |
| `Completed`, `Failed`, `Aborted` | Terminal. The resource stays as a record. | none |

### Admission, drafts and schedules

Phase `""` means "not yet admitted", nothing more. One admission block runs the two create-time checks and then writes `Pending` for every test, so a test that is mid-dispatch or on the barrier is never mistaken for a fresh one. (A test that an older binary left at `""` with TestRuns recorded skips both checks, so it reaches the reclaiming exits.) After the first Environment lookup succeeds, the test gets an owner reference to the Environment, so the Environment's finalizer can drain every test that ever found it.

- **Draft (`spec.suspended=true`).** The test is admitted at `Pending` and dispatches nothing while `status.testRuns` is empty. Patching `spec.suspended` to `false` lets it proceed. A draft skips the strict check that the Environment must be `Ready`, so it can be created against an Environment that is still provisioning. The state machine is immutable after the start: `spec.suspended` is read only before execution and only while no TestRun exists. The default is `false`, so a plain `kubectl apply` starts at once.
- **Schedule (`spec.startAt`).** It requires `spec.suspended=true`. The test waits at `Pending` with `Scheduled=True/ScheduledArmed`. At the deadline, with the Environment `Ready`, the operator patches `suspended=false` itself (`ScheduledFired`), and the normal machine takes over. Without `suspended`, `startAt` would be an immediate start with the time silently ignored, so the operator fails such a test at admission and the gateway rejects it with a 400. This is deliberately not a CRD CEL rule: a rule "startAt implies suspended" would also reject the operator's own fire-time patch and freeze every scheduled test.
- **Environment wait.** An active test whose Environment is not `Ready` and which has no TestRun waits (requeue 10 s, no status write; an Environment watch also wakes it). If TestRuns were already applied, the test fails and the partial run is reclaimed. While an Environment is being deleted nothing new dispatches.

### One test per Environment

`envOccupancyGate` serializes the tests of one Environment in a namespace. A sibling occupies the Environment while it has TestRuns applied before `Running`, is `Running` or `Exporting`, or has ended with `RunnersUnreclaimed`. Eligible tests that are not drafts and whose schedule has passed form a queue ordered by `creationTimestamp` (name breaks ties). A test that is not at the front, or whose Environment is occupied, is held at `Pending` with `Queued=True` and re-checked every 10 s. The decisive list is read through the uncached reader, because the TestRuns of siblings are persisted by direct status updates and a lagging cache could show two tests an empty Environment.

### Dispatch

`startK6` runs `dispatchOne` for each `perNodeLoad` entry that is not yet in `status.testRuns`, so a re-entry after a partial dispatch never re-applies a live run. For each generator:

1. `MirrorConfigMap`: server-side apply of the script ConfigMap (from the LoadTest's namespace) onto the generator, same name, namespace `default`, labelled with the LoadTest UID. k6-operator resolves `spec.script.configMap` on its own cluster, so the script must exist there.
2. Delete any stale TestRun of the same name (a rerun of the same LoadTest would otherwise inherit the old status), then wait until `Stage` answers `ErrNotFound`. A TestRun that is still present is rechecked every 3 s with no limit.
3. `Apply`: server-side apply of a `k6.io/v1alpha1 TestRun` (field owner `dfaas-operator`) with `parallelism: 1`, the labels `dfaas.io/loadtest-name` and `dfaas.io/node-id`, and the runner environment `DFAAS_SUMMARY_URL` (always), `DFAAS_SYNC_URL` (with `syncStart`) and `DFAAS_ASSET_BASE` (only when a management address was detected).
4. The `TestRunRef` is persisted at once, so a failure later in the loop leaves the applied runs visible to observe, abort and deletion.

The runner environment is computed once per generator per pass, and the same summary URL is handed to the filer reachability probe.

`perNodeLoad[].vus` and `duration` never reach k6. The runner obeys `options.scenarios` inside the script and the operator sets no TestRun field for either. They stay on the resource as a record of what was asked for. `duration` is what the SPA's per-generator progress bar counts against, so the SPA derives it from the scenarios (see [cross-repo-contract.md](cross-repo-contract.md#pernodeload-vus-and-duration)). Treat it as a declaration, never as a control input.

A dispatcher error charges the `dispatch-attempts` counter (budget 15, a spec edit resets it) and stamps `K6Dispatched=False` with `ScriptMirrorFailed`, `StaleCleanupFailed` or `ApplyFailed`, then retries after 10 s. Exhaustion ends the run as `Failed` with `DispatchFailed`. Before the first Apply, a `syncStart` test is failed if any generator resolves no GO URL, naming the generators.

#### Remote clients and the generator's namespace

The operator talks to a generator's k3s API directly over TLS on port 6443, with the kubeconfig in the Secret `<env>-<nodeID>-kubeconfig`. A client is rebuilt on every `Node` method call, with a 10 s request timeout, so a dead generator cannot hold the single worker for the operating-system TCP timeout. The management cluster's ServiceAccount needs no RBAC on remote TestRuns. A node that is absent from `status.k6Nodes[]` or has no kubeconfig Secret is an error, never a silent skip. Each caller decides what the error means: dispatch, observe and the barrier fail the test; the teardown names the generator as unconfirmed; log capture and the deletion poll skip it.

#### The filer reachability probe

A generator whose TestRun is applied may still be unable to reach the filer address its runner uploads to and, with `syncStart`, polls. After the apply loop, the operator starts one short-lived probe Pod per generator on that generator's k3s (`wget`, 30 s deadline, the k6-operator runner image) that fetches the recorded summary URL from the generator's own network. The probes are read during observe and barrier rounds that reached every generator, up to 2 minutes after the start. A probe that found the filer unreachable turns `K6Dispatched` into `True/DispatchedUnreachable` (status unchanged, so the reason change does not move the barrier budget's clock) with a message naming each failing generator, the URL and the error. The remedy in the message follows the URL's source: for a detected address, open the port or re-provision the Environment; for the fallback, `DFAAS_SYNC_PUBLIC_URL` must be reachable from every generator. A `SyncTimeout` later repeats the message. Probes are best-effort: an empty URL is skipped, and a probe that could not run is logged only. The probe Pods are deleted at the run end.

### Synchronized start

With `spec.syncStart=true`, the script's `setup()` polls `DFAAS_SYNC_URL` and the operator releases it. k6-operator's own starter is not fought. After `K6Dispatched=True`, `awaitSyncBarrier` keeps the test at `Pending`, polls a fleet round every 3 s and stamps `SyncReady=False/AwaitingRunners` (naming generators that did not answer) until every TestRun reports stage `started`. It then PUTs the GO object on the filer, stamps `SyncReady=True/GoPublished`, and only then stamps `status.startTime` and moves to `Running`, so `startTime` tracks the start of traffic. If GO was already published (a retry after a failed `finishDispatch`), it finishes the dispatch without publishing again.

The test fails through the run end, with `SyncReady=False/SyncTimeout`, when a generator is unusable, a TestRun is at stage `error`, a runner finished before the GO signal (it ran unsynchronized, and a partially synchronized run is invalid data), or the 5 minute budget (`syncWaitBudget`, counted from the `K6Dispatched=True` transition, covering both the runners parking and the GO publish) runs out. The GO object is deleted when every runner has finished, at every run end, and on deletion.

Stage `started` is a pod-level fact: it can be reported before the script's `setup()` reaches the barrier (a runner may still be fetching a payload image). Runners can therefore still start seconds apart. See [known-limitations.md](known-limitations.md#syncstart-does-not-align-runners-to-within-a-fraction-of-a-second). The address each generator dials is explained in [cross-repo-contract.md](cross-repo-contract.md#synchronized-start-specsyncstart).

### Observing

`observeK6` surveys every generator's stage once per round and never stops early. A generator that is unusable fails the test at once. A round in which any generator did not answer charges one `fetch-misses` attempt, however many generators missed (budget 15). The stages of the generators that did answer are still persisted, and `K6Healthy` reads `Unknown/FetchFailed` with `attempt n/15`. A complete round clears the counter. When every generator is done:

- no TestRun in `error`: `K6Healthy=True/AllFinished`, then `captureK6Logs`, deleting the GO object, stamping `endTime` and moving to `Exporting`;
- all in `error`: the test fails with `AllFailed`;
- some in `error`: the test fails with `PartialFailure`.

Failing a run in which any generator errored is deliberate: such a run is not the experiment that was asked for. There is no export and no log capture for it, and the runner logs stay on the generators until the LoadTest is deleted.

Every failed remote round is paced by one gate at the top of `Reconcile`: the counter write's own watch event would otherwise start the next attempt at once and burn a budget in seconds. The pacing interval is 10 s and is held in memory, so after an operator restart one round can come early. Generators are polled one after another, so K dead generators block the worker for K request timeouts per round.

`captureK6Logs` reads each runner pod's log through the generator's API (selector `app=k6,k6_cr=<testrun>,runner=true`, at most 256 KB) and stores it in one ConfigMap per generator in the LoadTest's namespace, owned by the LoadTest. A capture failure is recorded as placeholder text in the ConfigMap and never blocks the transition.

### Run end, abort and deletion

Every way a LoadTest ends goes through `endRun`. It re-reads the test uncached and does nothing if the test is already terminal. If runners may still be live (dispatch began, the phase is not `Exporting`, and some `perNodeLoad` entry has not been seen `finished`, `stopped` or `error`), it makes one teardown pass: `Delete` on every generator in the union of `perNodeLoad` and `status.testRuns` (which catches partial-dispatch races). The terminal phase is written whatever the remote answers. The verdict goes on `K6Healthy`:

- `RunnersReclaimed`: every target confirmed absent;
- `RunnersUnreclaimed`: the delete failed on a generator that held a recorded TestRun of this run;
- otherwise the run's own reason, naming what could not be confirmed (an unusable generator, an Environment that is gone).

When dispatch began, it also sweeps the filer (the GO object and the k6 summaries) and closes the in-progress Conditions: `MetricsExported=False/Skipped` unless the test completed, `SyncReady` from `AwaitingRunners` to `False`, `K6Dispatched` from `Unknown`/`InFlight` to `False`. All of this is one Transition through `phase()`, which does not requeue after a terminal write (ADR-0002).

A test that ended with `RunnersUnreclaimed` keeps occupying the Environment (`Queued=True/EnvBusy`, with a message saying that deleting the test releases it) and is swept again every 30 s until a delete succeeds or the test is deleted.

**Abort.** Patching `spec.stop=true` while the phase is `""`, `Pending` or `Running` ends the run as `Aborted` with `Ready=False/UserAborted` and the message `The test was aborted: spec.stop was set to true (UI Abort button or kubectl).`, and keeps the resource as a record. Drafts are abortable too (nothing was dispatched, so no remote call). In `Exporting` or a terminal phase the patch is ignored.

**Deletion.** The LoadTest finalizer `dfaas.dfaas.io/loadtest-finalizer` makes every deletion path run the remote cleanup first, because remote TestRuns carry no owner reference and cannot be garbage-collected across clusters. A test that has not ended is ended as `Aborted`. If dispatch began, the finalizer polls every generator until its TestRun is gone and deletes what is still there, for at most 2 minutes from the `DeletionTimestamp` (`deletionReclaimBudget`). Past that budget it releases without contacting any generator and logs them as unconfirmed, except a `RunnersUnreclaimed` test, which gets one last pass first. It deletes the mirrored script ConfigMap only when the remote copy's UID label still matches this LoadTest (a copy re-mirrored by another test under the same name is kept), and the probe Pod. A completed or failed record is never rewritten. A test that never dispatched makes no remote call; one whose Environment is already gone is released at once.

## Export

When a test enters `Exporting`, the reconciler does not create the exporter Job at once. It holds until `exportCooldown` has passed since `status.endTime`, stamping `MetricsExported=Unknown/ExportCooldown` with a countdown and requeueing for the remainder.

**The cool-down is a fixed one minute (`exportCooldown`), not a tunable.** The management Prometheus does not scrape the DFaaS nodes directly: it federates from each node's own Prometheus through `/federate` once per `server.global.scrape_interval` (10 s; the per-node Prometheus scrapes at 5 s, but that is only the first hop). Each node is pulled at its own offset, so the last sample inside the k6 window can be up to one interval older than `endTime`, by a different amount per node and per run, and no wait adds samples to a window that has already closed. The query window is therefore widened: the Job's `END_TIME` is `endTime` plus `exportTailWindow` (one federation interval), which puts at least one sample at or after the k6 finish on every node. The minute must cover two intervals: one for the last pull inside the window and one for the pull that lands after `endTime`. The deadline is computed from the persisted `status.endTime`, so an operator restart in the middle of the wait resumes the original deadline.

The interval is set in one place, `server.global.scrape_interval` in `internal/controller/monitoring/values/prometheus-values.yaml`. The operator reads it from that embedded file as `monitoring.FederationInterval`, so no Go constant restates it. `federation_interval_test.go` fails `make test` when two intervals no longer fit in the minute, and `prometheus_values_test.go` fails when the interval drops below the chart's 10 s `scrape_timeout` (Prometheus would refuse its configuration). A new value reaches the running Prometheus only at the next Environment provisioning. The SPA's preset metrics use `[5m]` rate windows, which must stay at least four times the federation interval, because `rate()` returns nothing when a window holds fewer than two samples.

**The exporter Job.** `<loadtest>-exporter-<uid8>-g<generation>-job` (bounded to 63 bytes), image from `DFAAS_EXPORTER_IMAGE`, `BackoffLimit: 2`, `ActiveDeadlineSeconds: 600`, owned by the LoadTest. Its environment:

| Variable | Value |
| --- | --- |
| `PROM_URL` | `http://prometheus-server.monitoring.svc.cluster.local:9090` |
| `METRICS_JSON` | `spec.metricsExport.metrics`, with a `raw` entry's empty `metricName` defaulted to its `query` |
| `START_TIME`, `END_TIME`, `STEP` | `status.startTime`, `status.endTime` plus the tail window, `spec.metricsExport.step` (default 15 s) |
| `EXP_NAME`, `LOADTEST_NAME`, `ENV_NAME` | names, used in rows and keys |
| `K6_SUMMARY_SOURCES` | JSON list of `{nodeId, url}`, one in-cluster filer summary URL per generator, built by the operator so the exporter never builds a filer path |
| `K6_LOG_DIR` | where the per-generator log ConfigMaps are projected (`/var/run/k6logs`) |
| `S3_*`, `S3_BUCKET_PREFIX`, `ENV_UID` | from the mirrored S3 config Secret, by `secretKeyRef`; present only when a config was resolved |

**The sink.** The config name is `Environment.spec.s3ConfigRef.name`, or `seaweedfs-default` when unset. `ensureMirroredS3Secret` copies that Secret from the `dfaas-s3` namespace into the LoadTest's namespace, because a Pod cannot mount a Secret across namespaces. The copy has no owner reference: it is shared by every LoadTest that uses the config, and a controller owner would block every later consumer with `AlreadyOwnedError`. It is never deleted (see [known-limitations.md](known-limitations.md#mirrored-s3-secrets-are-never-deleted)). Two failure modes differ on purpose. An explicit `s3ConfigRef` whose Secret is missing fails the test (`S3ConfigMissing`; the user asked for it). A missing default Secret (someone deleted it) degrades to a stdout dump so that the test still completes: the CSV is printed between `----- BEGIN CSV -----` and `----- END CSV -----` markers (recoverable with `kubectl logs`), and the `ExporterRunning` message names the fallback. The default Secret is created at operator startup, if absent, and never overwritten, so an administrator may repoint it.

**What the exporter writes.** The bucket is `<environment name, lowercased and sanitised, at most 56 characters>-<first 6 characters of the Environment UID>`, created on the first export and reused. Keys share one `<stamp>`, the end of the query window in compact UTC (`20060102T150405Z`), so a retried Job overwrites its own objects.

| Key | Contents |
| --- | --- |
| `metrics/<loadtest>/<stamp>.csv` | One row per (series, sample). Fixed columns `timestamp, node_id, value, loadtest, query_name, query_type, query_expr, query_comment`, then one column per Prometheus label (the union over the run, alphabetical, empty where a series lacks it; a label that collides with a fixed name gets a `_label` suffix). |
| `metrics/<loadtest>/query-status-<stamp>.csv` | One row per configured metric: series and samples returned, warnings, error. A query that matched nothing says so here. |
| `k6/<loadtest>/summary-<stamp>.csv` | Long format `loadtest, environment, window_start, window_end, node_id, metric, metric_type, stat, value, note`, plus one `dfaas_summary_fetched` row per expected generator (`1` or `0` and a reason). |
| `k6/<loadtest>/<nodeID>-summary-<stamp>.json` | Each fetched raw `handleSummary` JSON, verbatim. |
| `k6/<loadtest>/<nodeID>-<stamp>.log` | Each runner's captured log. |

Only the metrics CSV is fatal: the Job fails when queries were attempted and every one came back empty ("metrics export produced 0 data points"). The query-status CSV is uploaded first, so that the failure still leaves the diagnosis. Everything about the k6 summaries and logs warns and continues. The exporter ends the LoadTest `Completed` when the Job succeeds, which does not prove that a k6 summary was fetched ([known-limitations.md](known-limitations.md#a-raw-script-without-handlesummary-exports-no-k6-numbers)). The Prometheus label keys `node_id` and `node_type` are written by `ReconcileTargets` and read back by the exporter; they must change together.

## Monitoring stack

`monitoring.Manager.Deploy` installs three Helm releases into the shared `monitoring` namespace, once across Environments (an install the first time, an upgrade afterwards). The charts and values are embedded; Helm runs with `Wait=false`, so readiness is checked separately and an Environment without a default StorageClass waits in `ProvisioningMonitoring` with `monitoring pods not Ready yet`.

| Release | Chart | Notes |
| --- | --- | --- |
| `prometheus` | `prometheus-29.6.0` | Service `prometheus-server` on 9090, NodePort 30090. `scrape_interval` 10 s. Retention 7 days or 16 GB, 20Gi PVC. One scrape job, `dfaas-nodes`, that federates (`/federate`, `match[]={job!=""}`, `honor_labels`) from the targets in `/etc/prometheus/file_sd/*.json`, refreshed every 30 s. Alertmanager, node-exporter, kube-state-metrics and the pushgateway are disabled. |
| `grafana` | `grafana-10.5.15` | NodePort 30300, no persistence, anonymous visitors are `Admin` and the login form is off. One provisioned datasource (Prometheus) and one dashboard, `dfaas-live` (uid `dfaas-live`), provisioned from `dashboards/dfaas-live.json`. A dashboard edited in the Grafana UI is lost at the next restart. |
| `seaweedfs` | `seaweedfs-4.45.0-dfaas1` | `allInOne` mode: master, volume, filer and S3 gateway in one pod, one 10Gi PVC. The archive is the upstream 4.45.0 chart with one template patched (`fromToml` replaced by `dict`), because the pinned Helm SDK 3.14.4 does not define `fromToml`; see `assets.go`. |

**Scrape targets.** `ReconcileTargets` writes one JSON file per Environment into the shared ConfigMap `prometheus-targets` in `monitoring`, keyed `<namespace>_<name>.json`. It lists the DFaaS nodes only, as `<ip>:30909` with the labels `environment`, `node_id` and `node_type` (the node's `capacity`). It runs at the end of provisioning and again on every Ready pass, and writes nothing when the file is current. `CleanupTargets` removes the file on deletion. A key `<name>.json` from before the namespace was part of the key is deleted on the first write or cleanup that touches that Environment.

**RBAC.** The operator must never be able to mint ClusterRoles, so the charts' cluster-scoped RBAC is turned off in the values and `charts/dfaas/templates/monitoring-rbac.yaml` pre-creates the one ClusterRole the stack needs, `dfaas-prometheus-server`, bound to the ServiceAccount `prometheus-server`. The ClusterRole name is hard-coded in `server.useExistingClusterRoleName` of `prometheus-values.yaml` and in the template, and the template binds it to the ServiceAccount `prometheus-server`, whose name comes from `server.fullnameOverride` in the same values file; rename one and you must rename the others. Grafana is told only `rbac.namespaced: true`. The SeaweedFS values set `global.seaweedfs.createClusterRole: false` for the same reason. Running `make run` hides all of this, since a kubeconfig admin can create anything.

These SeaweedFS values are load-bearing and are covered by `seaweedfs_values_test.go`: `master.enabled`, `volume.enabled` and `filer.enabled` are `false` (those templates are guarded only by their own flag, not by `allInOne`, so leaving them true deploys a second full topology beside the all-in-one pod); `global.seaweedfs.createClusterRole` is `false`; and `s3.credentials.admin` must equal what `EnsureDefaultS3Config` writes into the default config Secret.

### Addresses and ports

All SeaweedFS addresses come from `monitoring/addresses.go`, and `seaweedfs_values_test.go` pins the embedded values against the same constants. Do not rebuild a filer URL by hand anywhere else, and build any VM-facing `host:port` through `FilerPublicBase` or `S3PublicBase` (they bracket IPv6).

The ports that must be reachable between machines are in the Network table of the [README](../README.md#requirements). Three more exist that nobody outside the node needs: 31112 on each DFaaS node is the OpenFaaS gateway, used by the playbook on the node itself; 30555 and 30666 on each DFaaS node are the HAProxy Data Plane API and runtime API, used by the dfaas-agent; and SeaweedFS listens in the cluster on 8333 (S3) and 8888 (filer), behind NodePorts 30900 and 30901. The UI's NodePort 30800 is set by the chart.

In the management cluster the SeaweedFS Service is `seaweedfs-all-in-one.monitoring.svc.cluster.local`. The exporter and the operator use that name; remote runners use the NodePorts. The operator's flags default to metrics on `:8080` and probes on `:8081`.

## Retry and requeue model

- **One worker per controller.** Reconciles of one controller are serialized.
- **Each reconciler states its own scheduling.** `statuswriter.Writer.Record` returns only an error ([ADR-0002](adr/0002-status-writer-never-decides-requeue.md)). The Environment's handlers return their own `RequeueAfter` and rely on the status watch; the LoadTest's `phase()` requeues at once except after a terminal write, because an immediate pass would read the pre-terminal cached copy and stamp in-progress Conditions on an ended test.
- **Status writes re-fetch the object on every attempt** (`RetryOnConflict`) to absorb informer-cache lag, stamp Conditions before the aggregate, and keep `LastTransitionTime` stable.
- **Bounded retries are counters.** Five generation-scoped annotations, all through `statuswriter.Budget` ([ADR-0003](adr/0003-all-retry-counters-generation-scoped.md)); a spec edit resets them. When the counter write itself fails, `Attempt` reports `CounterUnavailable` instead of a count of zero, the round is still surfaced, and the budget does not advance (the message then reads `?/N`).

| Counter | Object | Limit | On exhaustion |
| --- | --- | --- | --- |
| `ssh-attempts` | Environment | 3 | `Unreachable` (non-terminal) |
| `health-misses` | Environment | 3 | `Unreachable` (non-terminal) |
| `monitoring-attempts` | Environment | 5 | `Failed` (`HelmFailed`) |
| `dispatch-attempts` | LoadTest | 15 | `Failed` (`DispatchFailed`) |
| `fetch-misses` | LoadTest | 15 rounds | `Failed` |

| Wait | Interval | Bound |
| --- | --- | --- |
| Unreachable nodes, provisioning | 10 s | 3 rounds, then `Unreachable` |
| Ready probe | 60 s (20 s after a miss) | 3 rounds |
| `Unreachable` re-probe | 30 s | none |
| Ansible Job | 10 s | Job `BackoffLimit` 3 and 30 min deadline |
| Monitoring install | 10 s | 5 failures |
| Environment wait of a LoadTest | 10 s | none (the Environment watch also wakes it) |
| Queue | 10 s | none |
| Stale TestRun before apply | 3 s | none |
| Dispatch retry | 10 s | 15 attempts |
| Fleet round, running | 5 s | none while healthy |
| Failed remote round | 10 s | 15 rounds |
| Sync barrier | 3 s | 5 min |
| Export cool-down | the remainder | 1 min |
| Exporter Job | 5 s to 10 s | Job `BackoffLimit` 2 and 10 min deadline |
| `RunnersUnreclaimed` re-sweep | 30 s | until deleted |
| LoadTest deletion | 3 s (10 s after a node error) | 2 min |
| Environment deletion drain | 3 s | 3 min per test |

- **Unbounded on purpose.** A `JobCreationFailed` error is returned to controller-runtime and retried with its backoff, without a limit. The wait for a stale TestRun to disappear is unbounded.
